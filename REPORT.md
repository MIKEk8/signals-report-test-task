# Отчёт

Оба бага воспроизведены и исправлены в `common_function.php`, `Fnc::getTgSignalList()`. Каждое исправление — отдельный коммит.

## Баг 1. Заниженные R и неверные цены закрытия

**Причина.** `$col_take_profit` (число тейков сделки) объявлялся *до* цикла `while`, а не внутри него. Сделка прибавляла свои тейки к счётчику, оставшемуся от предыдущих, поэтому R и цена закрытия делились на всё большее N.

**Почему проявлялось именно так.**
- Первая сделка вкладки считалась правильно: счётчик стартовал с нуля. Это и значит «первая строка выглядит правильно».
- GMKN (sell, один тейк, закрыта по стопу) шла 2-й строкой вкладки, счётчик был 2, и результат получился −1/2 = −0.5. CHMF шла 4-й, к ней накопилось N=6 (проверено по данным), и −1/6 ≈ −0.17.
- Цена закрытия — это сумма `цена / N`, поэтому у CHMF вышло 219.25 вместо 1315.5 (1315.5 / 6).
- Ошибка затрагивала все отчёты, потому что счётчик тёк между сделками внутри одного вызова.

**Исправление.** Сброс `$col_take_profit = 0` перенесён внутрь цикла.

## Баг 2. Пропадающие сделки

**Причина.** Для прошлых месяцев условие было `date_closed BETWEEN '2026-08-01' AND LAST_DAY('2026-08-01')`. `LAST_DAY()` возвращает дату без времени, то есть `2026-08-31 00:00:00`. Всё, что закрыто 31-го после полуночи, в диапазон не попадает. Закрытая 31.08 в 18:40 SBER не попала в август. В сентябрь она не попала правильно: её месяц — август.

**Исправление.** Полуинтервал `date_closed >= '…-01' AND date_closed < DATE_ADD('…-01', INTERVAL 1 MONTH)`. Он работает с любой длиной месяца и не зависит от времени. Индекс по `date_closed` по-прежнему используется.

**Почему «не только SBER».** Это любая сделка, закрытая в последний день месяца. В августе на Мосбирже их было три: 14 + 3 = 17. В сентябре потерялась одна, так что вместо 24 строк стало 25.

### Серьёзное

1. **SQL-инъекция через `month` и `year`** [запуск]. `report_function.php:6-10` берёт `$_GET` без проверки, `common_function.php` вставляет значения в `LIKE '…%'` и в условия по `date_closed`. `?month=09'` отдаёт в HTML необработанное `mysqli_sql_exception` с текстом запроса и путями. Тот же класс: `$category_id`, `$tool_id`, `$tg_block_id`. Нужны prepared statements и проверка `month` ∈ `01..12`, `year` — четыре цифры.
2. **Отражённый XSS** [запуск]. `report.php:367` выводит `$month` и `$year` в `href` без экранирования: `?month="><script>…` встраивается в страницу. Остальные поля шаблона (`tiker`, `diraction`, `type`, цены, `r`) тоже выводятся как есть. `r` — `varchar`, который вводит аналитик [код].
3. **Один месяц, разные результаты, в зависимости от записи** [запуск]. Ветка «текущий месяц» выбирается нестрогим `$month == date('m')`. `?month=010` PHP считает равным `10`, но префикс `LIKE` получается `2026-010-` и ничего не находит: вместо 16 закрытых сделок страница показывает 0 и «ИТОГ R» 2.4 вместо 8.27, при этом выпадающий список показывает «Октябрь». То же с `10.0` и `1e1`.
4. **Выгрузка XLSX ломается на невалидном или «нестандартном» месяце** [запуск]. `create_xlsx.php:113` берёт `$fnc->array_month[$month]` без проверки. `month=9` (без нуля), `13`, `abc` и пустой `month` дают `Undefined array key`, ответ получается `text/html` с бинарным хвостом вместо файла. Страница при `month=9` при этом отрисовывается, и ссылка «Скачать XLSX» ведёт на битую выгрузку. `year` попадает в имя файла без экранирования.
5. **Деление на ноль** [синтетика, воспроизведено на `Fnc`]. Закрытая сделка с `price_open == stop_loss_rash` и сработавшим тейком — `DivisionByZeroError`, падает вся вкладка рынка и страница целиком. Открытая сделка с заполненной датой тейка и всеми `take_profit* = 0` делит на `$col_take_profit = 0` с тем же результатом. Если же такая сделка закрыта по цене, равной стопу, ошибки нет, R = −1.

### Расчёт R и итоги

6. **Float в сравнении `R >= 0`** [синтетика, на данных БД не встречается: просмотрено 324 строки за январь–октябрь]. R сделки суммируется из частей и не округляется после суммы. Для buy 100 / стоп 90 и тейков 100.9 / 109 / 130 (два сработали, остаток по стопу) получается −5.55e-17: сделка уходит в «Убыточные», в «Итого» выводится «-0», а доходность — `-5.5511151231258E-17%`. Нужно `round(R, 2)` после суммирования. Когда именно это возникает — в разделе «Условия появления R = −5.5e-17» ниже.
7. **Ручной `r` теряется у открытых сделок** [синтетика]. Проверка `is_numeric($res['r'])` есть только в ветке закрытых. У открытой сделки с `r='1.5'` без тейков R становится пустым, а с одним сработавшим тейком пересчитывается в 1.0. README говорит «если в поле `r` число, он не пересчитывается» без оговорки про открытые сделки; впрочем, для открытых там же сказано «R считается только по сработавшим тейкам», так что требование неоднозначно.
8. **Ручной `r` с запятой не распознаётся** [синтетика]: `is_numeric('1,5')` ложно, значение молча пересчитывается. Причина — `r varchar(100)`.
9. **Закрытая сделка без тейков** [синтетика]: R = 0, `price_close = 0`, `d1 = 0%`, попадает в «Прибыльные», хотя вышла по 110 при входе 100 и стопе 90. Открытая с `take_profit = 0`, `take_profit_2 = 120` и заполненной датой первого тейка получает R = −10.0 (считается от цены 0).
10. **Запасной стоп молча искажает расчёт** [синтетика]. При `stop_loss_rash = 0` берётся `stop_loss`. Если и он 0, риск равен цене входа: вход 100, выход 120 дают R = 0.2 вместо ошибки. Стоп с «неправильной» стороны от входа (buy со стопом 110 при входе 100) переворачивает знак: выход 120 даёт R = −2.
11. **Избыточная эвристика на строке 159** [запуск]. Если `take_profit == price_close` и даты тейка нет, дата подставляется из `date_closed` (сравнение float через `==`, только для первого тейка). На результат это не влияет: при `take_profit == price_close` обе ветки считают одно и то же (проверено на тейке 2: R = 1.5 и цена закрытия 115 в обоих случаях). Это мёртвый код, а не дефект, но он вводит в заблуждение: выглядит как правило, которого на самом деле нет.
12. **`diraction` — свободный `varchar` без `ENUM`/`CHECK`** [код]. На расчёт R это не влияет: формулы buy и sell математически совпадают (`(выход−вход)/(вход−стоп)` и `(вход−выход)/(стоп−вход)` равны), поэтому `'BUY'`, `'buy '` и любое другое значение считаются одинаково (проверено запуском). Влияние ограничено подписью в таблице.
13. **Сделка, закрытая в прошлом месяце и удалённая или отменённая в текущем** [синтетика, воспроизведено], в отчёт текущего месяца не попадает, хотя README требует показывать удалённые и отменённые «в этом месяце». Условие `(is_closed=0 or date_closed LIKE … or date_created LIKE …)` её отсекает. В текущих данных таких сделок нет.
14. **`d1`/`d2` пусты у открытых сделок с R** [запуск] (например, PLZL, R=0.7), хотя R входит в «ИТОГ R». README говорит «доходность при 1% равна R%» без исключения для открытых. Колонка `risk` нигде не используется, 2% зашито как `R*2`.
15. **«Всего сделок» определяется по `r != "-"`**, а не по флагам статуса [код]. Сейчас совпадает с README, но ручное `r='-'` у живой сделки выпадет из итога.
16. **При ручном R колонка «Цена закрытия» остаётся сырой `price_close`**, а не средней ценой выхода по частям, как требует README [запуск].
17. **`round(1/N, 2)` при N=3** даёт −0.99, а не −1 у сделки, закрытой по стопу. Прямое следствие правила «каждая часть округляется до 0.01», но пользователь увидит −0.99. Спорный пункт, решение за аналитиками.

## Условия появления R = −5.5e-17

Код накапливает R сделки как `$r = $r + round(часть, 2)` по очереди для тейков 1, 2, 3 (`common_function.php:223-324`). Каждая часть — десятичное число с двумя знаками, но хранится как двоичный `double`. Если математически сумма частей равна 0.00, а двоичное сложение не сокращается точно, остаётся «пыль» порядка 1e-17. Итог после суммы не округляется, а сравнения `R >= 0` и `R < 0` (`getItogDataSignalTable`) делаются по сырому значению.

Что нужно для воспроизведения (перебор всех комбинаций в сотых долях):

1. **Три части, то есть три тейка.** При одном и двух тейках не бывает: для двух частей `a + (−a)` в double точно равно нулю (801 пара из 801 дала 0), для одной части сумма равна самой части.
2. **Сумма трёх округлённых частей ровно 0.00 в десятичной записи и не распадается на пару `a + (−a)`.** Например, `+0.03 + 0.30 − 0.33`: первые два тейка сработали, третья часть закрыта по стопу (`−round(1/3, 2) = −0.33`), а `0.03 + 0.30` в double не равно в точности `0.33`.
3. **Состав частей не важен.** Подойдёт любая тройка с нулевой суммой: части по тейкам, по `price_close` или по стопу. Порядок влияет на результат: если стоп-часть (−0.33) идёт первой, ненулевой результат дают 16 пар из 32, если третьей — 10 из 32.

Как часто: из 67 951 троек в диапазоне от −1.50 до +1.50 с нулевой суммой ненулевой результат даёт 30 040 (44%), знак поровну: 15 020 отрицательных и 15 020 положительных. Для самого вероятного сценария «две части в плюс, третья по стопу (−0.33), первые две в сумме 0.33» ненулевой результат даёт 10 пар из 32, и все десять отрицательные (например, `0.03 + 0.30 − 0.33 = −5.55e-17`).

Последствия:
- **Отрицательная «пыль»** переводит сделку, которая по README должна быть безубыточной и «прибыльной» (R ≥ 0), в «Убыточные». «Прибыльных» становится меньше, «Убыточных» больше, процент прибыльных на странице и в XLSX меняется.
- **«-0» в итогах:** `round(-5.5e-17, 2)` даёт `-0.0`, на странице выводится «-0».
- **Строка доходности:** `d1 = '-5.5511151231258E-17%'`, `d2 = '-1.1102230246252E-16%'` вместо `0%`.
- **Положительная «пыль»** (`6.9e-18`, `2.8e-17`) безвредна для классификации, но даёт такие же уродливые строки в колонках доходности.

В текущих данных БД такого нет: по всем 324 строкам трёх рынков за январь–октябрь ни одного ненулевого R с модулем меньше 1e-9. Для этого нужна именно сделка с тремя тейками, у которой три округлённые части дают ноль. Исправление — `round($r, 2)` после суммирования частей (и тест на сделке из примера выше).
